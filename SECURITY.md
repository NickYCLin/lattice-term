# Security policy

LatticeTerm handles remote-host identities and authentication material. Security reports are treated as private by default.

## Reporting a vulnerability

Please do not open a public issue for a suspected vulnerability or include credentials, private keys, host inventories, or exploit details in public discussions.

Use the repository's private [GitHub Security Advisory form](https://github.com/NickYCLin/lattice-term/security/advisories/new). Include:

- the affected commit or version;
- operating system and architecture;
- reproduction steps with sanitized test hosts;
- expected and observed behavior;
- potential impact;
- a suggested fix, if available.

You should receive an acknowledgement through GitHub after the report is reviewed. No response-time guarantee is offered during the pre-1.0 stage.

## Supported versions

LatticeTerm is currently pre-1.0. The latest GitHub Release and the latest commit on `main` receive security fixes; fixes land on `main` first and are included in the next applicable release. Older pre-1.0 releases are not maintained as separate support lines.

## Current security boundaries

- Connection profiles persist in the operating system's per-user application-data directory and contain no passwords, private keys, passphrases, or tokens. A device dialed by ID is remembered as an ordinary profile holding its nine-digit identity and relay address, both non-secret addressing metadata; the pairing code is never stored and is asked for on every connection.
- SSH terminal sessions use the Rust russh engine. Passwords default to one connection attempt; when the user explicitly chooses to remember one, it is written only after authentication succeeds and only to the operating system credential store.
- SFTP uses the same russh transport and strict host-key trust store, with a separate OS credential entry per profile. Remote paths reject control characters, mutating actions are user initiated, and overwrites and deletes require confirmation in the UI. Large transfers use bounded streaming; uploads remain in a private same-directory staging file until the declared byte count is complete, then protect and replace an existing target. Cancellation, failure, and session disconnect remove incomplete staging files. The legacy whole-payload read/write IPC remains capped at 32 MiB.
- SSH host keys are checked strictly against `known_hosts.json`. Unknown keys require an explicit comparison, changed keys are blocked, and the Key Vault view manages the same real trust store.
- Remote text editing is a separate, user-initiated, 1 MiB UTF-8 path, not a blind overwrite upload. It checks content-hash/metadata revisions and retains the displaced original as a recovery copy. Drafts stay in memory, including after session disconnection. SFTP v3 cannot guarantee ACL/hardlink preservation, atomic compare-and-swap, hostile parent-path race isolation or power-loss durability without a server fsync extension. Use host-native tools for special ACL semantics. Lattice Remote only advertises editing on Linux/macOS hosts; Windows hosts fail closed until file security descriptors can be preserved reliably. No additional MCP write grant is introduced. A save can commit before its acknowledgement is lost; preserve the draft and reload rather than blindly retrying. See [text-editing boundaries](docs/REMOTE_TEXT_EDITING.zh-TW.md).
- For SFTP files with group/other mode bits, each save additionally requires explicit access-change acknowledgement, enforced in the backend with a false default. Inheriting a parent ACL can grant additional users access despite identical POSIX bits; acknowledgement accepts that risk, it does not preserve an ACL. Owner-only files retain a zero group/other mask without this extra confirmation. No automatic chmod of the original is performed.
- Lattice Remote starts only after the local user explicitly enables sharing. Direct mode refuses wildcard or multicast bindings and uses a five-minute, one-session pairing code. Relay mode connects outward, keeps serving until stopped, and uses a permanent nine-digit device identity plus a generated 128-bit token or a case-sensitive 6-64 character ASCII password. Returning viewers reject changed device keys through trust-on-first-use pinning. A first-use pin is persisted only after the Agent's valid encrypted Hello; incomplete or rejected pairing cannot poison the saved identity.
- New Remote handshakes use OPAQUE (opaque-ke, Ristretto255/TripleDH/SHA-512/Argon2) before Noise, including hex-shaped passwords and generated tokens. A domain-separated HKDF-SHA256 of the mutually authenticated OPAQUE session key becomes the Noise PSK; the password itself is never a static Noise PSK. The login context binds the protocol and relay device ID. Registration stays local to the host and its ephemeral record is not sent over the network. Legacy v2/v3 viewers are opt-in only: v3 requires the original random token, and v2 short codes additionally require a pre-existing device pin checked before the proof. There is no automatic downgrade. This composition has local regression coverage, not an independent security audit; see [pairing details](docs/PAIRING_PASSWORD.zh-TW.md).
- Lattice Remote protocol version 2 carries either the primary display or a PTY-backed shell through Noise XXpsk3 with ChaChaPoly and BLAKE2s. Sessions are view-only by default. Mouse/keyboard or terminal input requires `--allow-input`, while file browsing, upload, and download require an independently authorised single `--file-root`. Remote paths cannot escape that canonical root, and incomplete uploads are not published.
- The relay endpoint is non-secret connection metadata. LatticeTerm remembers it in WebView local storage and collapses it in routine dialogs after first use, but this is a usability choice rather than a security control. Public endpoints must use `wss://`; the relay sees device IDs and routing metadata but only forwards end-to-end encrypted session bytes and never receives the pairing code. Loopback connections from a reverse proxy are exempt from the relay's direct-source rate limit by default, so a public ingress must either supply per-client abuse controls itself or start the relay with `--client-ip-header` naming the header it sets to the real client address, which restores the per-IP limit for proxied traffic. That header is trusted only from loopback peers.
- A relay device identity contains its registration token and Noise private key. It is created on first read, which happens only once the user selects relay sharing in the share dialog: opening the application, or sharing over the local network only, never mints one. On Unix, new and existing identity files are forced to owner-only mode `0600`; the relay registry stores only token hashes and is also owner-only. Fixed pairing codes are not persisted by the integrated host and are sent to the child Agent through stdin, not process arguments. Standalone unattended deployments should use an owner-only `--pair-code-file`; command-line `--pair-code` values may be visible in process listings.
- Lattice Remote protocol decoding rejects agent names over 256 bytes or containing control characters, close reasons over 1,024 bytes, frames over 8 MiB, dimensions over 16,384 px per edge, more than 32 Mi pixels, unsafe terminal messages, and out-of-bound file chunks before they reach the WebView or host resources. Five consecutive pairing failures stop the Agent. A device-local, cross-process budget also reserves attempts before password authentication: five unfinished/failed attempts in a rolling ten-minute window block new attempts even after restart. A successful authentication refunds only its own reservation. Missing write access, corrupt state and unsafe paths fail closed. The secret-free state uses a file lock and atomic replacement next to the identity file; service managers should still avoid unconditional restarts.
- Web RDP runs IronRDP in an isolated child process. The password is sent once over stdin, never appears in process arguments or profile files, and the browser surface receives display frames rather than network credentials. Optional persistence uses the same OS credential store and occurs only after a successful connection.
- Web RDP enforces TLS certificate validation. A self-signed certificate is rejected first; the UI may retry only with the exact SHA-256 certificate fingerprint explicitly approved for that attempt. NLA/CredSSP is required and legacy graphical TLS login is disabled.
- Screenshots and recordings are initiated explicitly in the session toolbar and are produced from the remote Canvas only. Media stays in WebView memory until the user downloads it; LatticeTerm does not upload or persist captures in application storage.
- Agent Fleet launches local AI CLIs in native PTYs with the current operating-system user permissions. Executables and arguments remain separate and are never interpolated into a shell command. LatticeTerm does not inspect or separately persist model API keys. To restore visible context after a normal app restart, it may retain each Agent's latest 256 KiB terminal-output tail in an XChaCha20-Poly1305 encrypted, device-local file; its random key stays in Windows Credential Manager, macOS Keychain, or Linux Secret Service and never enters the WebView. If the operating-system credential store is unavailable, terminal output remains memory-only. Every registered CLI is terminated when the user stops it or the app exits.
- Custom Agent Fleet inputs reject control characters and enforce limits on labels, paths, arguments, terminal dimensions, and IPC input size. Working directories are canonicalized before launch. On Windows, `.exe`/`.com` run directly; npm-style `.cmd`/`.bat` shims run through `cmd /d /c` with the verbatim-path prefix removed and the matching Node runtime placed first on `PATH`, never through an interpolated shell string.
- Optional Linux sandboxing uses bubblewrap: the whole filesystem is bound read-only, and only the working directory, the CLI's own existing state directories under the home directory, an account-profile directory when one is in use, and `/tmp` are writable (a CLI state directory that does not exist yet, and Claude Code's `.claude.json`, are created empty before the launch so a first sign-in works inside the sandbox; existing files are never touched); the CLI's policy files inside that state (Claude `settings.json`, Codex `config.toml`/`rules`, Gemini/Qwen `settings.json`, Cursor `hooks.json`/`mcp.json`) are re-bound read-only so a sandboxed run cannot plant a hook or MCP server for a later unsandboxed launch. PIDs are unshared and the sandbox dies with LatticeTerm. It confines writes only: reads and network are not restricted, so anything readable in the home directory remains readable, and the interface says so. The option is offered only after `bwrap` was probed to work (kernels or AppArmor policies that block unprivileged user namespaces make it unavailable) and a launch that asks for it refuses rather than running unconfined. It is a file-scope policy, not a container.
- A cross-CLI handoff no longer pastes the earlier transcript into the new CLI's terminal; it is written to `handoffs/handoff-*.md` under the application data directory (owner-only, random name, swept after 24 hours) and the CLI receives a one-line pointer. The brief is the same bounded, text-only export as before and contains no credentials.
- A session launched with "keep in the background" is owned by `lattice-term agent-daemon`, the same binary started detached by the desktop. It listens only on a user-private local endpoint in the application data directory (a 0600 Unix socket, or a named pipe on Windows) and accepts a connection only after a greeting carrying the owner-only token file next to it; the desktop attaches as a thin proxy and the daemon runs the unchanged session registry, so the reporter listener, per-session tokens and integration files never leave that process. While no window is attached the daemon also runs the chat automations the window handed it (never with per-call approval; `ask` becomes read-only) and records each run's events to an owner-only file under the data directory, handed over once to the next window. The daemon exits by itself after 60 idle seconds with no sessions and no enabled automations, ends every session on `SIGTERM` or an explicit stop, and logs only connection and error lines (no prompts, output or tokens) to a 0600 log file capped at 1 MiB. Sessions not marked for the background stay in the desktop process and end with it, as before.
- `lattice-term mcp` exposes shared background Fleet sessions over stdio. Session metadata, terminal content, control and starting saved background plans require separate user grants; arbitrary launch commands and desktop-owned Fleet terminals are not exposed. SSH/SFTP use a separate live-desktop grant path described below. Both queued and immediate prompts require official CLI readiness and no unfinished desktop input or pending startup instructions. Prompts use bracketed paste and reject terminal control characters. Revoking control drops pending MCP prompts while preserving desktop work; already accepted writes cannot be undone, and stopping remains available even when a terminal write blocks. Cancel can clear MCP prompts, interrupt the running turn on the CLIs whose own interface documents an interrupt key, or terminate the entire session.
- A remote screen (RDP, VNC or a Lattice Remote display share) reaches an MCP client only as single still pictures, and only after the user shares that exact connection: a screen grant carries the screen permission and nothing else, binds to the one live run of that session so a reconnection ends it, and allows one capture every two seconds. Frames are retained only while such a grant exists — the newest one, in memory, never on disk — and are dropped the moment sharing ends or the session closes; a frame too large to deliver whole is refused rather than truncated. Pointer and keyboard input require the separate consent and capture receipt described below; there is no continuous stream or recording, and each capture is recorded in the MCP history as metadata only.
- New desktop shares atomically grant metadata access with `readOutput: false`. Terminal output and excerpts require explicit content permission; withdrawing it leaves metadata and control grants intact. Control does not imply content access. The desktop requires the negotiated `mcpOutputScopes` capability before offering new shares or changing content scope, and never interrupts a CLI to upgrade the daemon. Legacy shares retain their existing content access and remain revocable. Allowing MCP to launch saved plans explicitly grants sharing, content access and control to the resulting sessions. Session metadata may itself be sensitive.
- Pending and queued content replies retain the original grant generation through both daemon and stdio writers. Revocation invalidates those replies even after reauthorization. If a slow writer has already sent part of a frame, its MCP/observer stream closes rather than completing the old payload; the client can reconnect without ending the CLI or withdrawing metadata/control grants. Bytes already transmitted cannot be recalled.
- MCP writes require a request ID. Concurrent identical requests share one operation; different parameters cannot reuse an ID. The daemon retains at most 256 results for 15 minutes after completion and rejects fresh work when full. Unauthorized or invalid fresh requests do not reserve result slots. A replay rechecks current grants; timeouts may have unknown outcomes, and deduplication does not survive daemon restart or expiry. Launch-plan changes invalidate an in-flight launch before its session is shared; an unchanged settings refresh does not. Settings failures attempt to withdraw launch permission and report any unconfirmed withdrawal.
- MCP stdio requests, output queues and raw observer connections have bounded concurrency, line lengths and queued frames. Slow or overloaded observers are disconnected without blocking other clients; disconnecting the adapter does not terminate existing CLI sessions. Terminal bytes are read by cursor from the daemon's 256 KiB tail, in pages of at most 64 KiB plus up to 4 KiB to complete one character or control sequence, never pushed to observers as events. Revocation and daemon loss wake pending waits with distinct results. Tool output excludes executables, arguments, account directories, process IDs and native session IDs. Per-session grants live in daemon memory and end with the session; the launch switch is persisted with saved plans. The UI shows the latest client action and logs metadata only. The adapter never starts a daemon and never returns its owner-only token. Terminal output is untrusted data, as the server instructions state.
- Chat mode runs each Claude Code and Gemini turn as one headless CLI process (`claude -p --output-format stream-json`, `gemini --output-format stream-json`) with the prompt written to stdin, never on the command line. Codex runs as one `codex app-server` per thread that stays alive between turns (ended after 15 idle minutes, when the thread is deleted, or when LatticeTerm exits); every turn resends the approval policy, sandbox policy, working directory and model, and a request the server sends while no turn is active is declined. On Unix the process gets its own process group and a stop kills the whole group, so a command the CLI left running cannot keep the turn alive; stdout/stderr readers start before stdin is written and stderr is kept as a bounded tail. Per-tool-call approvals for Claude Code and Codex travel over the CLI's own bidirectional protocol; requests the window cannot render are declined so a turn cannot hang. Inherited `CLAUDECODE` and reporter variables are removed from the child so a chat turn cannot be treated as a nested or fleet-reporting session. Threads are kept only in the WebView's local storage with bounded size (tool output truncated, total capped); the CLI keeps the full transcript and all credentials. Account profiles store only a name and a configuration directory. Scheduled automations never run with per-call approval and default to read-only.
- Agent semantic reports are accepted only by an ephemeral loopback listener. Each PTY child receives a separate 256-bit random token; reports are capped at 4 KiB, time out, and can select only one of four lifecycle states. The reporter cannot send terminal input, launch processes, read files, or retrieve prompts. Processes running as the same operating-system user remain inside this local trust boundary because they may be able to inspect another process environment.
- GitHub Actions dependencies are pinned to full commit SHAs and checked by `npm run actions:check`. The default workflow token is read-only; write scopes are granted only to the Release Please, artifact-upload, and release-publish jobs that require them. Updater signing material is injected only into the signing steps and is never stored in the repository or application bundle.
- Linux GTK3 currently requires `glib` 0.18. LatticeTerm vendors the crates.io 0.18.5 source and applies gtk-rs upstream commit `05dff0e` for RUSTSEC-2024-0429; the vendored release-mode iterator tests guard the affected `VariantStrIter` path until Tauri can adopt a newer GTK stack.
- Password persistence uses Windows Credential Manager, macOS Keychain, or Linux Secret Service through keyring-rs; the optional master-password vault uses Argon2id and XChaCha20-Poly1305. SSH private keys are read only from a user-selected local path and are not copied into profile storage. SSH tunnels and VNC are implemented; VNC is explicitly identified as unencrypted and should be carried through an SSH tunnel on untrusted networks. Stronghold is not planned because the upstream project is archived; importing private-key material into either credential backend remains unimplemented.
- Tauri IPC exposes scoped profile-storage, Agent Fleet PTY, SSH/SFTP-session, Lattice Remote, Web RDP input/session, trusted-host, credential-status/existence/deletion, runtime-summary, and updater operations. Agent Fleet input events are capped at 64 KiB and target only an existing in-memory session. SFTP file bytes cross IPC only after an explicit transfer or bounded text-editor operation. There is deliberately no IPC command that returns a saved password to the WebView, and no arbitrary local filesystem access. The main window permits destruction after the editor's native-close confirmation; this does not grant filesystem or network access.
- Logs and screenshots must not contain secrets or private infrastructure details.

The desktop-only MCP history keeps at most 256 metadata entries (a versioned file capped at 256 KiB), including Agent writes, remote operations and remote grant changes. A bounded background worker writes private atomic snapshots for restart recovery: Unix owner-only modes and Windows protected current-user DACLs are verified, and detected links, unsafe permissions, malformed data or external changes stop persistence without clearing the existing file or blocking ordinary CLI work. The UI distinguishes pending, persisted, memory-only and unavailable storage. Abrupt exit can lose pending entries or leave temporary files. This is not an append-only, complete or tamper-evident ledger, and does not protect against a malicious same-user process or administrator. Observers cannot read it. It does not collect prompts, request IDs, raw errors, credentials or launch arguments; self-reported client labels can themselves contain sensitive information and must be chosen accordingly. Accepted operations are not proof of successful tasks; request deduplication still does not survive restart.

Remote MCP tools require a live desktop bridge and separate, initially disabled scopes on an already trusted SSH/SFTP session. They never authenticate, accept host keys, expose saved credentials or invoke arbitrary Tauri commands. The daemon routes only to the owning desktop connection; both ends enforce grants, and revocation or disconnect invalidates access. SSH exec uses a dedicated noninteractive channel and a user-approved fixed command, with bounded stdout/stderr, explicit exit status/signal and deadlines. Closing that channel does not prove all remote descendants have stopped. File tools accept opaque root IDs and relative paths between approved local/remote roots, reject detected links and traversal, cap transfers at 8 MiB and do not overwrite existing destinations. SFTP realpath/open races require a trusted server and directory management; this is not a server-side chroot. Fixed commands retain the SSH account's privileges and are not constrained by the file roots. Remote operation IDs are retained in a bounded desktop-only ledger for 15 minutes; unknown outcomes must not be blindly retried with new IDs. Remote output and file names are untrusted data.

MCP observers use daemon protocol 2, distinct from desktop protocol 1. Legacy daemons ignore unknown role fields, so the adapter must use a version those daemons reject before returning private session data. The desktop negotiates MCP support before sending administration frames; unsupported commands fail locally without dropping existing desktop sessions. An outdated daemon must be restarted after existing work finishes; the application never forcibly restarts it for MCP. This protects protocol compatibility, not against a malicious process already running as the same OS user with access to the desktop token.

These statements describe the current source tree, not a security audit or certification.

### MCP screen input

Screen capture does not authorize keyboard or pointer input. Input requires a
separate live-connection grant and, for Lattice Remote, host-approved control.
Each discrete input batch consumes a client-bound capture receipt within ten
seconds; changed pixels, dimensions, connection generation, revocation or local
viewer takeover invalidate it. Coordinates use captured frame pixels. A tool
submission is not confirmation of a remote application outcome. Once accepted,
input cannot be rolled back; partial RDP/VNC writes close the engine to avoid
stranded pressed keys. Input metadata is audited without text, keys or coordinates.


### SSH remote Fleet workspaces

The `remote_fleet` tool uses a dedicated exec channel on an already trusted SSH
connection, invoking only the executable, data directory and workspace the user
approved. The model cannot change paths, add executable arguments or select an
arbitrary MCP method. No local daemon token or SSH credential is forwarded.
Both local scopes and existing remote MCP grants apply. The remote greeting
fixes a canonical directory; session operations and actual launch requests must
remain within that directory or its descendants. Symlink escapes are rejected.
The directory filter limits routing and launch selection, not the remote CLI's
OS privileges or network access; use a separately configured sandbox where needed.

Remote capability negotiation refuses peers that ignore workspace scope. Scoped
adapters cannot recursively delegate desktop, host or Fleet tools. Each channel
has a 384 KiB total reply budget, 64-message limit and 12-second deadline; it
closes without terminating the remote daemon's independently owned PTYs.
Revocation blocks new work and pending results, but cannot undo accepted actions.
Deduplication binds the local grant/client and canonical remote workspace and
retains the existing fifteen-minute, process-lifetime boundary. Unknown outcomes
must be inspected before any new request ID is used. Audits retain operation
metadata, not prompts, terminal text, credentials or workspace paths.

Windows Fleet uses an explicitly selected platform and a fixed encoded PowerShell bootstrap with literal native arguments. Local drive paths are required; UNC/device paths, drive roots, ambiguous components and alternate data streams are refused. The same remote workspace and per-session grants still apply. Windows OpenSSH host and installed-app acceptance are recorded separately in `docs/MCP-WINDOWS-FLEET-ACCEPTANCE.zh-TW.md`.

### Lattice Remote command execution

Windows hosts may explicitly enable cmd / PowerShell commands independently of screen input and file sharing. This grants execution as the sharing account, including access outside the shared file root; it is not a filesystem sandbox or privilege elevation. Commands run in owned kill-on-close Job Objects, with bounded concurrency, execution time and output. Cancellation cannot undo changes already made by a command. Command content and output are not recorded in application history.
